# 콘텐츠 작성 가이드

이 문서는 포트폴리오의 모든 콘텐츠 작성 기준을 정의한다.

---

## 1. 목적

이 문서는 포트폴리오의 모든 콘텐츠 작성 기준을 정의한다.

페이지, 프로젝트, 시스템 기획, 게임 분석 등 모든 콘텐츠는 이 기준을 따른다.

---

## 2. 기본 원칙

- 간결하게 작성한다.
- 근거 중심으로 작성한다. (주장에는 항상 이유/데이터가 따른다)
- 결과보다 과정을 강조한다. (어떻게 사고했는지가 핵심이다)
- 수치를 적극 활용한다. (지표, 기간, 규모 등)
- 불필요한 미사여구를 금지한다.

---

## 3. 프로젝트 문서 작성 규칙

### 3.1 구성 순서

각 프로젝트는 아래 순서를 따른다.

1. 프로젝트 개요
2. 담당 역할
3. 목표
4. 문제 정의
5. 접근 과정
6. 시스템 설계
7. 핵심 기능
8. 결과
9. 회고

순서를 임의로 바꾸지 않는다.

---

### 3.2 섹션별 작성 원칙 (Content Authoring Guide)

모든 프로젝트가 같은 품질을 유지하도록, 9개 섹션 각각에 대해 다음 네 가지를 기준으로 작성한다.

- **무엇을 써야 하는가** — 이 섹션이 반드시 담아야 할 내용
- **무엇을 쓰면 안 되는가** — 다른 섹션의 책임을 침범하거나 이 프로젝트의 신뢰도를 깎는 서술
- **채용담당자가 무엇을 보고 싶은가** — 2~3분 스크리닝(`docs/DESIGN_SYSTEM.md` §3) 흐름에서 이 섹션이 하는 역할
- **시니어 게임기획자가 무엇을 평가하는가** — 심층 검토(`docs/INFORMATION_ARCHITECTURE.md` §2.4 User Flow) 흐름에서 이 섹션으로 판단하는 역량

기본 원칙(§2)과 문체(§6)는 9개 섹션 모두에 공통으로 적용되며 아래에서 반복하지 않는다.

#### 1. 프로젝트 개요 (`overview`)

- 써야 하는 것: 이 프로젝트가 무엇이고 왜 존재했는지 한두 문단으로 요약한 핵심 정체성.
- 쓰면 안 되는 것: 장르/플랫폼/기간/팀 규모(헤더 메타 정보, `docs/DATA_MODEL.md` §5.1) 반복 서술. "담당 역할"(2번) 내용을 미리 서술.
- 채용담당자: 이 프로젝트가 지원 직무(시스템/콘텐츠 기획자)와 관련 있는지 즉시 판단할 수 있는가.
- 시니어 기획자: 과장 없이 프로젝트의 스코프를 정확히 진술했는가.

#### 2. 담당 역할 (`contribution`)

- 써야 하는 것: 이 프로젝트에서 본인이 정확히 무엇을 소유(오너십)했는지, 실제 산출물 중심으로. 헤더의 `role`(짧은 라벨)을 서술형으로 풀어낸 내용이며, `skills`(태그)는 이 역할과 연결된 스킬만 나열한다.
- 쓰면 안 되는 것: "팀과 함께"처럼 책임 소재가 불명확한 서술. 직함만 나열(예: "시스템 기획자로 참여")하고 무엇을 기획했는지 밝히지 않는 것. 목표/시스템 설계(3, 6번)의 내용을 미리 설명.
- 채용담당자: 지원 직무와 실제 기여 내용이 일치하는가.
- 시니어 기획자: 책임 범위가 명확한가 — 이 사람이 정확히 무엇을 오너십했는가.

#### 3. 목표 (`goal`)

- 써야 하는 것: 이 프로젝트/시스템이 달성하려던 목표. 플레이어 관점(무엇을 재미있게/의미 있게 만들려 했는가)과 제품/지표 관점을 함께 다룰 수 있다.
- 쓰면 안 되는 것: "재미있는 게임을 만들고 싶었다" 같은 추상적 목표. 아직 일어나지 않은 결과(8번)를 목표에 미리 서술.
- 채용담당자: 목적의식을 갖고 일하는 기획자인가.
- 시니어 기획자: 목표가 검증 가능한 형태로 구체화되어 있는가.

#### 4. 문제 정의 (`problem`)

- 써야 하는 것: 목표를 가로막던 구체적 문제. 데이터/유저 피드백/플레이테스트 등 근거 기반 서술(§2).
- 쓰면 안 되는 것: 문제와 해결책을 뒤섞어 서술(해결책은 5번의 몫). "문제가 있었다"처럼 근거 없이 뭉뚱그린 서술.
- 채용담당자: 스스로 문제를 정의할 수 있는 사람인가.
- 시니어 기획자: 증상과 근본 원인을 구분해 서술했는가 — 문제 정의의 해상도.

#### 5. 접근 과정 (`approach`)

- 써야 하는 것: 검토한 대안들과 그중 하나를 선택한 이유(트레이드오프). "어떻게 사고했는가"가 핵심(§2).
- 쓰면 안 되는 것: 대안 비교 없이 최종 결과물(6번)만 결론적으로 서술. 검토한 대안이 하나도 없었던 것처럼 서술.
- 채용담당자: 일하는 스타일과 사고방식을 확인.
- 시니어 기획자: 대안 비교와 트레이드오프 판단 능력 — 가장 예민하게 평가하는 섹션 중 하나.

#### 6. 시스템 설계 (`systems`, `documents`)

- 써야 하는 것: `docs/CONTENT_GUIDE.md` §4의 7개 항목(목적/플레이어 경험/시스템 구조/플로우/데이터/예외 처리/기대 효과)을 시스템 하나당 하나의 `ProjectSystem` 항목으로 채운다. 여러 시스템(예: 전투/성장)이 있으면 항목을 나눈다. `documents`는 이 서술을 뒷받침하는 근거 자료로만 첨부한다.
- 쓰면 안 되는 것: 여러 시스템을 하나의 항목에 뭉뚱그려 서술. 예외 처리를 생략 — 설계가 완결되지 않았다는 인상을 준다.
- 채용담당자: (2차 대상) 실제 설계 문서가 존재한다는 신뢰만 확인.
- 시니어 기획자: 가장 깊이 읽는 섹션 — 구조/플로우/데이터/예외 처리가 하나의 일관된 시스템으로 앞뒤가 맞는가, 예외 상황까지 고려했는가.

#### 7. 핵심 기능 (`features`, `gallery`)

- 써야 하는 것: 시스템 설계(6번)의 결과가 실제 플레이어에게 어떻게 보이는지(기능명 + 설명). `gallery`로 시각적 증거를 제시하며, 모든 이미지는 §7(이미지 사용 규칙)의 설명·캡션·목적을 반드시 포함한다.
- 쓰면 안 되는 것: 시스템 설계(6번)에서 이미 다룬 "왜/어떻게 설계했는가"를 반복. 설명·캡션·목적이 없는 이미지 첨부.
- 채용담당자: 가장 빠르게 눈으로 확인하는 구간 — 스크린샷 위주로 훑는다.
- 시니어 기획자: 설계(6번)와 실제 기능(7번)의 일관성 — 설계한 것이 실제로 기능까지 이어졌는가.

#### 8. 결과 (`result`)

- 써야 하는 것: 목표(3번) 대비 실제 성과. 반드시 수치 중심(§2)이며, 목표에서 제시한 기준과 1:1로 대응해야 한다.
- 쓰면 안 되는 것: 목표에 없던 새 기준으로 성과를 사후 정당화. 근거 수치 없는 정성적 표현("좋은 반응을 얻었다")만 단독으로 사용.
- 채용담당자: 빠른 스크리닝의 핵심 구간(`docs/INFORMATION_ARCHITECTURE.md` §2.4) — 성과를 낸 프로젝트인지 즉시 판단.
- 시니어 기획자: 목표-결과의 정합성과 수치의 신뢰성(과장 여부).

#### 9. 회고 (`retrospective`)

- 써야 하는 것: 결과 이후 스스로 발견한 한계·배운 점과 다음에 어떻게 적용할지. 아쉬운 점을 포함하는 것을 권장한다.
- 쓰면 안 되는 것: 문제 정의/접근 과정(4, 5번)의 요약 재서술. 회고를 성과 자랑으로 대체. 근거 없는 자기비하나 감정적 표현(§6).
- 채용담당자: (2차 대상) 성숙도·자기 인식 신호로만 참고.
- 시니어 기획자: 실패를 인정하고 구조적 개선안을 도출하는 능력 — 주니어와 시니어를 가르는 핵심 신호.

### 3.3 데이터 작성 템플릿

`data/projects.template.json`은 `docs/DATA_MODEL.md` §5와 100% 동일한 필드를 갖춘 빈 템플릿이다. 값은 전부 `""`/`[]`(불리언은 `false`)이며, 실제 콘텐츠를 추가할 때 이 템플릿을 복사해 `data/projects.json` 배열에 항목으로 붙여넣는다. 필드를 추가하거나 삭제하지 않는다 — 새 필드가 필요하면 먼저 `docs/DATA_MODEL.md`를 갱신하는 Architecture Decision을 거친다.

배열 필드 안에 들어가는 개별 항목의 모양은 다음과 같다(`docs/DATA_MODEL.md`의 해당 절 참고):

**`systems`의 항목 하나 (`ProjectSystem`, §5.3 · 작성 원칙은 위 3.2의 "6. 시스템 설계", §4 참고)**

```json
{
  "name": "",
  "purpose": "",
  "playerExperience": "",
  "structure": "",
  "flow": "",
  "data": "",
  "exceptionHandling": "",
  "expectedEffect": ""
}
```

**`features`의 항목 하나 (`ProjectFeature`, §5.4 · 작성 원칙은 위 3.2의 "7. 핵심 기능")**

```json
{ "name": "", "description": "" }
```

**`documents`의 항목 하나 (`ProjectDocument`, §5.6 · `type`은 `"pdf" | "ppt" | "docx" | "markdown" | "notion" | "other"`)**

```json
{ "type": "", "title": "", "url": "" }
```

**`gallery`의 항목 하나 (`ProjectGalleryImage`, §5.7 · `type`은 `"screenshot" | "wireframe" | "uml" | "erd" | "concept" | "other"` · 설명·캡션·목적은 §7 필수)**

```json
{ "type": "", "src": "", "description": "", "caption": "", "purpose": "" }
```

**`links`의 항목 하나 (`ProjectLink`, §5.8 · `type`은 `"github" | "figma" | "notion" | "youtube" | "deployment" | "other"`)**

```json
{ "type": "", "label": "", "url": "" }
```

`type` 필드들은 전부 닫힌 집합(union)이라 위 목록 중 하나의 문자열 값으로 채운다 — 빈 문자열로 남겨두지 않는다(다른 문자열 필드와 달리 `type`은 렌더링 분기 기준이라 항상 유효한 값이 있어야 한다).

## 4. 시스템 기획 작성 규칙

시스템 기획 문서는 항상 다음을 포함한다.

- 목적
- 플레이어 경험
- 시스템 구조
- 플로우
- 데이터
- 예외 처리
- 기대 효과

---

## 5. 게임 분석 작성 규칙

게임 분석 문서는 항상 다음을 포함한다.

**분석 대상과 목적** (분석 전체를 소개하는 도입 정보)
- 분석 대상 — 어떤 게임을 분석하는지
- 분석 목적 — 이 분석으로 무엇을 보여주려는지

**분석 관점 (시스템 / 콘텐츠 / UX)** — 세 관점 각각에 아래 4가지를 동일하게 적용한다 (`docs/DATA_MODEL.md` §6.2의 systemAnalysis/contentAnalysis/uxAnalysis에 대응).
- 핵심 요소 — 이 관점에서 가장 중요하게 다루는 대상 (예: 시스템 관점 → 핵심 시스템, 콘텐츠 관점 → 핵심 콘텐츠, UX 관점 → 핵심 경험)
- 장점
- 문제점
- 개선안

**결론** — 세 관점을 종합한 결론. 배운 점을 포함한다.

순서를 임의로 바꾸지 않는다.

> **변경 이력**: 이전에는 "분석 대상/분석 목적/핵심 시스템/장점/문제점/개선안/배운 점"을 하나의 평평한 7개 목록으로 나열했다. 이는 서로 다른 두 추상화 수준 — 분석 전체의 도입 정보(대상/목적)와, 시스템 관점에만 한정된 것처럼 보이지만 실제로는 세 분석 관점 모두에 반복 적용되어야 하는 4항목 템플릿(핵심 요소/장점/문제점/개선안) — 을 구분 없이 섞고 있었다. "핵심 시스템"이라는 표현도 콘텐츠·UX 관점에는 그대로 쓸 수 없어 "핵심 요소"로 일반화했다. 개념(7개)은 그대로 유지하고 계층만 명확히 했다 — `docs/DATA_MODEL.md` §6, `types/analysis.ts`와 함께 동기화되었다.

---

## 6. 문체

채용 담당자를 대상으로 한다.

- 객관적으로 작성한다.
- 전문적으로 작성한다.
- 읽기 쉽게 작성한다.
- 불필요한 감정 표현을 금지한다.

---

## 7. 이미지 사용 규칙

이미지는 반드시 다음을 가진다.

- 설명 (이미지가 무엇을 보여주는지)
- 캡션 (짧은 요약 문구)
- 목적 (이 이미지를 넣은 이유)

설명·캡션·목적이 없는 이미지는 사용하지 않는다.

---

## 8. PDF 작성 규칙

PDF는 웹과 동일한 구조를 유지한다.

- 섹션 순서는 웹 페이지 구조를 따른다.
- 웹에 없는 내용을 PDF에만 추가하지 않는다.
- 웹과 PDF의 정보가 서로 다르지 않도록 유지한다.

---

## 9. 체크리스트

문서를 작성하기 전에 다음을 확인한다.

- [ ] 콘텐츠 유형(프로젝트/시스템 기획/게임 분석)에 맞는 구성 순서를 따랐는가
- [ ] 각 항목에 근거(수치, 데이터, 사례)가 포함되어 있는가
- [ ] 결과뿐 아니라 과정(문제 정의 → 접근 → 설계)이 드러나는가
- [ ] 불필요한 미사여구나 감정 표현이 없는가
- [ ] 문체가 객관적이고 전문적인가
- [ ] 모든 이미지에 설명·캡션·목적이 포함되어 있는가
- [ ] PDF 버전이 웹 구조와 동일한가
- [ ] 문서 내 수치와 사실이 정확한가

---

## 10. Project Review Checklist (작성 완료 후 검수 기준)

§9는 "작성 전에 확인하는 것"이고, 이 절은 "작성 완료 후 통과해야 하는 것"이다. 모든 프로젝트는 `data/projects.json`에 반영되기 전 아래 세 체크리스트를 모두 통과해야 한다 (`docs/PROJECT.md` §10 Quality Gate의 Content Review / Recruiter Review / Senior Planner Review 단계에 각각 대응).

세 체크리스트는 서로 다른 검토자의 관점을 대표하므로 순서대로 적용한다 — Content Review가 §3.2 기준 자체 충족 여부를 먼저 확인하고, 이를 통과한 프로젝트만 Recruiter Review(빠른 스크리닝)와 Senior Planner Review(심층 검토) 대상이 된다.

### 10.1 Content Review Checklist

섹션별로 아래 항목을 확인한다. 각 항목은 §3.2 각 섹션의 "써야 하는 것 / 쓰면 안 되는 것" 기준을 검증 가능한 질문으로 바꾼 것이다.

■ Overview (`overview`)
- [ ] 프로젝트를 한 문장으로 이해할 수 있는가
- [ ] 헤더 메타 정보(장르/플랫폼/기간/팀, `docs/DATA_MODEL.md` §5.1)나 담당 역할(2번) 내용을 반복하지 않는가

■ Role (`contribution`)
- [ ] 담당 범위가 명확한가
- [ ] 본인의 기여가 팀 전체의 기여와 구분되는가 ("팀과 함께" 같은 책임 불명확 서술이 없는가)

■ Goal (`goal`)
- [ ] 프로젝트 목표가 명확한가
- [ ] 목표에 대응하는 성공 기준이 존재하는가 — 8번(결과)과 1:1로 대응할 수 있는 형태인가

■ Problem (`problem`)
- [ ] 해결하려는 문제가 명확한가
- [ ] 문제의 중요성과 근거(데이터/유저 피드백/플레이테스트)가 함께 설명되는가

■ Approach (`approach`)
- [ ] 해결 과정이 논리적인가
- [ ] 검토한 대안과 최종 선택 사이의 트레이드오프 판단이 보이는가

■ System Design (`systems`)
- [ ] 설계 이유(purpose)가 설명되는가
- [ ] 확장성과 예외 상황(exceptionHandling)이 고려되었는가

■ Core Features (`features`)
- [ ] 핵심 기능이 프로젝트 목표(3번)와 연결되는가
- [ ] 시스템 설계(6번)에서 이미 다룬 "왜/어떻게 설계했는가"를 반복하지 않는가

■ Result (`result`)
- [ ] 정량적 결과가 존재하는가
- [ ] 프로젝트 성과가 목표(3번) 대비 객관적으로 설명되는가 — 근거 수치 없는 정성적 표현만 단독으로 쓰이지 않는가

■ Retrospective (`retrospective`)
- [ ] 단순 요약이 아니라 다음 프로젝트에서도 재사용 가능한 인사이트를 제공하는가
- [ ] 문제 정의/접근 과정(4, 5번)을 그대로 재서술하지 않는가

이 체크리스트를 통과하지 못한 프로젝트는 Quality Gate의 Content Review 단계를 통과할 수 없다.

### 10.2 Recruiter Review Checklist

채용담당자의 빠른 스크리닝 흐름(`docs/DESIGN_SYSTEM.md` §3, `docs/INFORMATION_ARCHITECTURE.md` §2.4 User Flow)을 기준으로 검증한다.

- [ ] 2~3분 안에 프로젝트를 이해할 수 있는가
- [ ] 핵심 성과(Result)가 빠르게 눈에 띄는가
- [ ] 지원 직무(시스템/콘텐츠 기획자, `docs/PROJECT.md` §4)와의 관련성이 명확한가
- [ ] 문장이 간결한가 (§6 문체 기준)
- [ ] 9단계(§3.1) 순서를 따라 읽는 흐름이 자연스러운가

### 10.3 Senior Game Designer Review Checklist

시니어 기획자의 심층 검토 흐름(`docs/INFORMATION_ARCHITECTURE.md` §2.4 User Flow)을 기준으로 검증한다.

- [ ] 문제 정의가 명확한가 (증상과 근본 원인이 구분되는가)
- [ ] 설계 의도가 드러나는가 (purpose/expectedEffect가 실제 결과와 연결되는가)
- [ ] Trade-off가 설명되는가 (접근 과정에서 검토한 대안이 보이는가)
- [ ] 확장성이 고려되었는가 (시스템 설계의 exceptionHandling, 향후 콘텐츠 증가 대응)
- [ ] 데이터 기반 의사결정이 보이는가 (문제 정의/결과가 수치·근거로 뒷받침되는가)
- [ ] 시스템 간 관계를 이해할 수 있는가 (여러 `systems` 항목이 있을 경우 서로 어떻게 연결되는지)

## 11. Project Content Workflow

이 절은 §3(작성 규칙)·§10(검수 기준)을 하나의 실행 순서로 연결한다 — "무엇을 어떻게 쓰는가"와 "무엇을 통과해야 하는가"는 정의되어 있었지만, 그 사이를 잇는 "어떤 순서로 진행하는가"가 없었다. 브랜치 단위 Git 작업 순서(`docs/GIT_WORKFLOW.md` §2)의 "작업" 단계를 콘텐츠 작업에 한해 구체화한 것이다.

```
1. 프로젝트 자료 수집
   ↓
2. 초안 작성
   ↓
3. DATA_MODEL.md 기준 JSON 작성
   ↓
4. Content Review Checklist (§10.1)
   ↓
5. Recruiter Review Checklist (§10.2)
   ↓
6. Senior Game Designer Review Checklist (§10.3)
   ↓
7. 수정
   ↓
8. Quality Gate 통과
   ↓
9. data/projects.json 반영
   ↓
10. 최종 검증
```

| 단계 | 내용 | 산출물 / 기준 |
|------|------|----------------|
| 1. 프로젝트 자료 수집 | 기획서, 개발 문서, 회의록, Git Commit, PPT, 실제 구현 화면 등 원본 자료를 모은다 | `docs/CONTENT_GUIDE.md` §13 Content Source Rule의 출처 체인 |
| 2. 초안 작성 | 수집한 자료를 근거로 9단계 구성(§3.1)과 섹션별 작성 원칙(§3.2)에 따라 문장을 작성한다 | 근거 없는 문장은 작성하지 않는다 — §12 Evidence Rule |
| 3. DATA_MODEL.md 기준 JSON 작성 | 초안을 `data/projects.template.json`(§3.3) 형태로 옮긴다 | 필드 추가/삭제 없이 템플릿 구조를 그대로 따른다 |
| 4~6. 세 체크리스트 | JSON 초안을 대상으로 Content → Recruiter → Senior Game Designer 순서로 자체 검수한다 | §10.1~§10.3, 통과하지 못한 항목을 모두 기록 |
| 7. 수정 | 체크리스트에서 실패한 항목을 반영해 2~3단계로 되돌아가 다시 작성한다 | 세 체크리스트를 모두 통과할 때까지 반복 |
| 8. Quality Gate 통과 | 세 체크리스트를 모두 통과한 시점 | `docs/PROJECT.md` §10 Quality Gate의 4·6·7단계(Content/Recruiter/Senior Planner Review) 충족 확정 |
| 9. data/projects.json 반영 | Quality Gate를 통과한 JSON만 실제 데이터 파일에 병합한다 | 이 시점에 비로소 Quality Gate 3단계(Real Contents)가 ✅로 전환된다 |
| 10. 최종 검증 | 실제 렌더링 결과로 화면 흐름과 완성도를 확인하고, `tsc`/`eslint`/`next build`/route를 검증한다 | Quality Gate 5단계(UX Review)·8단계(Portfolio Quality) 충족 확인 |

**단계 순서와 Quality Gate 번호가 다른 이유**: `docs/PROJECT.md` §10의 8단계는 완성도의 계층(어느 것이 어느 것을 전제하는가)을 나타내는 번호이지, 이 워크플로우의 실행 순서와 항상 같지는 않다. Content/Recruiter/Senior Planner Review(4·6·7단계)는 실제로는 Real Contents(3단계)가 `data/projects.json`에 반영되기 **이전**, 초안/JSON 상태에서 먼저 통과되어야 한다 — 검수를 통과하지 못한 콘텐츠가 실제 데이터 파일에 들어가는 것을 막기 위한 순서다. UX Review(5단계)와 Portfolio Quality(8단계)는 반대로 실제 데이터가 반영된 뒤 화면에 렌더링해야만 확인할 수 있어 9단계 이후(10. 최종 검증)에 위치한다.

이 워크플로우는 Projects(`data/projects.json`)에 한정된다. Analysis 등 다른 콘텐츠 유형은 아직 동일한 워크플로우가 정의되지 않았다 (`docs/PROJECT.md` §12 Technical Debt 참고).

## 12. Evidence Rule

모든 콘텐츠는 주장(Claim)이 아닌 근거(Evidence)를 기반으로 작성한다 — §2 기본 원칙의 "근거 중심으로 작성한다"를 섹션별로 구체화한 규칙이다. 근거를 찾을 수 없는 문장은 작성하지 않는다 — 추측이나 과장으로 빈 자리를 채우지 않는다.

| 섹션 | 요구되는 근거 | 근거가 없을 때 |
|------|----------------|-----------------|
| 1. 개요 (`overview`) | 없음 — 아래 각 섹션의 근거로 뒷받침되는 요약이어야 한다 | 다른 섹션에 근거가 갖춰진 뒤 마지막에 작성한다 |
| 2. 담당 역할 (`contribution`) | 실제 산출물(기획서, 커밋, 구현 화면 등)로 확인 가능한 담당 범위 | 산출물로 증명할 수 없는 역할은 서술하지 않는다 |
| 3. 목표 (`goal`) | 기획서/기획 회의록 등에 기록된 목표 | 사후에 지어낸 목표를 적지 않는다 — 회고(9번)에서 실제로 목표가 없었음을 밝힌다 |
| 4. 문제 정의 (`problem`) | 데이터, 유저 피드백, 플레이테스트 기록 | 근거 없이 "문제가 있었다"고 뭉뚱그리지 않는다 (§3.2 4번과 동일 기준) |
| 5. 접근 과정 (`approach`) | 검토한 대안이 기록된 회의록/기획서, 실제 의사결정 기록 | 대안 비교 기록이 없으면 있었던 것처럼 서술하지 않는다 |
| 6. 시스템 설계 (`systems`) | 실제 시스템 기획서/개발 문서 (`documents`로 첨부) | 근거 문서가 없는 시스템은 항목으로 추가하지 않는다 |
| 7. 핵심 기능 (`features`) | 실제 구현 화면, 커밋, 스크린샷(`gallery`) | 구현되지 않은 기능은 "핵심 기능"에 포함하지 않는다 |
| 8. 결과 (`result`) | 정량적 지표(로그, 애널리틱스, 리텐션, 플레이테스트 결과 등 수치 자료) | 수치 근거가 없으면 정성적 표현만으로 단독 서술하지 않는다 (§3.2 8번과 동일 기준) |
| 9. 회고 (`retrospective`) | 목표(3번)·결과(8번)와 대조 가능한 기록, 실제 후속 개선 반영 사례 | 근거 없는 자기평가는 감상으로 취급하고 배제한다 |

근거의 구체적 출처 유형은 §13 Content Source Rule을, 근거를 콘텐츠에 연결하는 방법은 §14 Traceability Rule을 따른다.

## 13. Content Source Rule

포트폴리오 콘텐츠는 아래 체인을 거쳐 만들어진다. 체인의 앞쪽일수록 원본에 가깝고, 뒤쪽일수록 가공된 자료다 — 포트폴리오 콘텐츠는 이 체인의 마지막 산출물이며, 그 자체로는 근거가 될 수 없다(자기 참조).

```
기획서
  ↓
개발 문서
  ↓
회의록
  ↓
Git Commit
  ↓
PPT
  ↓
실제 구현 화면
  ↓
포트폴리오 콘텐츠
```

| 출처 | 성격 | 주로 뒷받침하는 섹션 |
|------|------|------------------------|
| 기획서 | 의도와 목표가 기록된 1차 자료 | 목표(3), 시스템 설계(6) |
| 개발 문서 | 시스템의 실제 구조/데이터가 기록된 자료 | 시스템 설계(6) |
| 회의록 | 의사결정과 대안 검토 과정이 기록된 자료 | 접근 과정(5) |
| Git Commit | 실제 작업 이력과 담당 범위가 기록된 자료 | 담당 역할(2), 핵심 기능(7) |
| PPT | 발표/보고 목적으로 요약된 자료 | 개요(1), 결과(8) |
| 실제 구현 화면 | 최종 결과물 자체 | 핵심 기능(7), 결과(8) |

체인 뒤쪽 자료(PPT, 실제 구현 화면)만 있고 앞쪽 원본(기획서, 개발 문서)이 없는 경우, 없는 원본을 지어내지 않는다 — 확보한 자료 범위 안에서만 근거를 표기한다(§14 Traceability Rule).

## 14. Traceability Rule

각 콘텐츠는 어떤 원본 자료(§13)를 근거로 작성되었는지 추적 가능해야 한다. `data/projects.json`(`docs/DATA_MODEL.md` §5)은 필드 추가가 금지된 고정 스키마이므로, 출처 정보를 위한 필드를 새로 추가하지 않는다 — 대신 콘텐츠 작성 과정에서 별도의 **작성 워크시트**로 관리한다.

- 작성 워크시트는 9단계 섹션(§3.1)마다 인용한 출처를 `[출처유형: 구체적 식별자]` 형태로 표기한다.
  - 예: `[기획서: 전투시스템_기획서_v2.pdf]`, `[회의록: 2024-03-10 스프린트 리뷰]`, `[Git Commit: a1b2c3d]`
- 워크시트는 `data/projects.json`에 반영되지 않는 내부 자료다 — 포트폴리오 방문자에게 노출되지 않는다.
- Content Review Checklist(§10.1)를 적용하기 전, 각 섹션에 최소 하나 이상의 출처가 표기되어 있는지 먼저 확인한다 — 출처가 없는 섹션은 Content Review 대상이 아니라 §12 Evidence Rule 위반으로 우선 반려한다.
- `documents`(§5.6)에 첨부되는 자료는 워크시트의 출처 표기와 반드시 일치해야 한다 — 워크시트에 없는 자료를 `documents`에만 첨부하지 않는다(둘은 같은 근거를 가리켜야 한다).
- 워크시트 파일이 실제로 어디에 위치하는지(`docs/projects/<slug>/evidence.md`)는 `docs/ARCHITECTURE.md` §11 Project Identifier Rule을 따른다 — 이 문서는 워크시트의 내용 규칙만 정의하고, 위치·명명 규칙은 중복 정의하지 않는다.

이 규칙은 Projects에 한정된다. Analysis 등 다른 콘텐츠 유형의 Evidence/Source/Traceability 매핑은 아직 정의되지 않았다 (`docs/PROJECT.md` §12 Technical Debt 참고).
