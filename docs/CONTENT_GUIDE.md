# 콘텐츠 작성 가이드

이 문서는 포트폴리오의 모든 콘텐츠 작성 기준을 정의한다.

---

## 1. 목적

이 문서는 포트폴리오의 모든 콘텐츠 작성 기준을 정의한다.

페이지, 프로젝트, 시스템 기획, 게임 분석 등 모든 콘텐츠는 이 기준을 따른다.

---

## 2. 기본 원칙

- 간결하게 작성한다.
- 근거 중심으로 작성한다. (주장에는 항상 이유/데이터가 따른다)
- 결과보다 과정을 강조한다. (어떻게 사고했는지가 핵심이다)
- 수치를 적극 활용한다. (지표, 기간, 규모 등)
- 불필요한 미사여구를 금지한다.

---

## 3. 프로젝트 문서 작성 규칙

### 3.1 구성 순서

각 프로젝트는 아래 순서를 따른다.

1. 프로젝트 개요
2. 담당 역할
3. 목표
4. 문제 정의
5. 접근 과정
6. 시스템 설계
7. 핵심 기능
8. 결과
9. 회고

순서를 임의로 바꾸지 않는다.

---

### 3.2 섹션별 작성 원칙 (Content Authoring Guide)

모든 프로젝트가 같은 품질을 유지하도록, 9개 섹션 각각에 대해 다음 네 가지를 기준으로 작성한다.

- **무엇을 써야 하는가** — 이 섹션이 반드시 담아야 할 내용
- **무엇을 쓰면 안 되는가** — 다른 섹션의 책임을 침범하거나 이 프로젝트의 신뢰도를 깎는 서술
- **채용담당자가 무엇을 보고 싶은가** — 2~3분 스크리닝(`docs/DESIGN_SYSTEM.md` §3) 흐름에서 이 섹션이 하는 역할
- **시니어 게임기획자가 무엇을 평가하는가** — 심층 검토(`docs/INFORMATION_ARCHITECTURE.md` §2.4 User Flow) 흐름에서 이 섹션으로 판단하는 역량

기본 원칙(§2)과 문체(§6)는 9개 섹션 모두에 공통으로 적용되며 아래에서 반복하지 않는다.

#### 1. 프로젝트 개요 (`overview`)

- 써야 하는 것: 이 프로젝트가 무엇이고 왜 존재했는지 한두 문단으로 요약한 핵심 정체성.
- 쓰면 안 되는 것: 장르/플랫폼/기간/팀 규모(헤더 메타 정보, `docs/DATA_MODEL.md` §5.1) 반복 서술. "담당 역할"(2번) 내용을 미리 서술.
- 채용담당자: 이 프로젝트가 지원 직무(시스템/콘텐츠 기획자)와 관련 있는지 즉시 판단할 수 있는가.
- 시니어 기획자: 과장 없이 프로젝트의 스코프를 정확히 진술했는가.

#### 2. 담당 역할 (`contribution`)

- 써야 하는 것: 이 프로젝트에서 본인이 정확히 무엇을 소유(오너십)했는지, 실제 산출물 중심으로. 헤더의 `role`(짧은 라벨)을 서술형으로 풀어낸 내용이며, `skills`(태그)는 이 역할과 연결된 스킬만 나열한다.
- 쓰면 안 되는 것: "팀과 함께"처럼 책임 소재가 불명확한 서술. 직함만 나열(예: "시스템 기획자로 참여")하고 무엇을 기획했는지 밝히지 않는 것. 목표/시스템 설계(3, 6번)의 내용을 미리 설명.
- 채용담당자: 지원 직무와 실제 기여 내용이 일치하는가.
- 시니어 기획자: 책임 범위가 명확한가 — 이 사람이 정확히 무엇을 오너십했는가.

#### 3. 목표 (`goal`)

- 써야 하는 것: 이 프로젝트/시스템이 달성하려던 목표. 플레이어 관점(무엇을 재미있게/의미 있게 만들려 했는가)과 제품/지표 관점을 함께 다룰 수 있다.
- 쓰면 안 되는 것: "재미있는 게임을 만들고 싶었다" 같은 추상적 목표. 아직 일어나지 않은 결과(8번)를 목표에 미리 서술.
- 채용담당자: 목적의식을 갖고 일하는 기획자인가.
- 시니어 기획자: 목표가 검증 가능한 형태로 구체화되어 있는가.

#### 4. 문제 정의 (`problem`)

- 써야 하는 것: 목표를 가로막던 구체적 문제. 데이터/유저 피드백/플레이테스트 등 근거 기반 서술(§2).
- 쓰면 안 되는 것: 문제와 해결책을 뒤섞어 서술(해결책은 5번의 몫). "문제가 있었다"처럼 근거 없이 뭉뚱그린 서술.
- 채용담당자: 스스로 문제를 정의할 수 있는 사람인가.
- 시니어 기획자: 증상과 근본 원인을 구분해 서술했는가 — 문제 정의의 해상도.

#### 5. 접근 과정 (`approach`)

- 써야 하는 것: 검토한 대안들과 그중 하나를 선택한 이유(트레이드오프). "어떻게 사고했는가"가 핵심(§2).
- 쓰면 안 되는 것: 대안 비교 없이 최종 결과물(6번)만 결론적으로 서술. 검토한 대안이 하나도 없었던 것처럼 서술.
- 채용담당자: 일하는 스타일과 사고방식을 확인.
- 시니어 기획자: 대안 비교와 트레이드오프 판단 능력 — 가장 예민하게 평가하는 섹션 중 하나.

#### 6. 시스템 설계 (`systems`, `documents`)

- 써야 하는 것: `docs/CONTENT_GUIDE.md` §4의 7개 항목(목적/플레이어 경험/시스템 구조/플로우/데이터/예외 처리/기대 효과)을 시스템 하나당 하나의 `ProjectSystem` 항목으로 채운다. 여러 시스템(예: 전투/성장)이 있으면 항목을 나눈다. `documents`는 이 서술을 뒷받침하는 근거 자료로만 첨부한다.
- 쓰면 안 되는 것: 여러 시스템을 하나의 항목에 뭉뚱그려 서술. 예외 처리를 생략 — 설계가 완결되지 않았다는 인상을 준다.
- 채용담당자: (2차 대상) 실제 설계 문서가 존재한다는 신뢰만 확인.
- 시니어 기획자: 가장 깊이 읽는 섹션 — 구조/플로우/데이터/예외 처리가 하나의 일관된 시스템으로 앞뒤가 맞는가, 예외 상황까지 고려했는가.

#### 7. 핵심 기능 (`features`, `gallery`)

- 써야 하는 것: 시스템 설계(6번)의 결과가 실제 플레이어에게 어떻게 보이는지(기능명 + 설명). `gallery`로 시각적 증거를 제시하며, 모든 이미지는 §7(이미지 사용 규칙)의 설명·캡션·목적을 반드시 포함한다.
- 쓰면 안 되는 것: 시스템 설계(6번)에서 이미 다룬 "왜/어떻게 설계했는가"를 반복. 설명·캡션·목적이 없는 이미지 첨부.
- 채용담당자: 가장 빠르게 눈으로 확인하는 구간 — 스크린샷 위주로 훑는다.
- 시니어 기획자: 설계(6번)와 실제 기능(7번)의 일관성 — 설계한 것이 실제로 기능까지 이어졌는가.

#### 8. 결과 (`result`)

- 써야 하는 것: 목표(3번) 대비 실제 성과. 반드시 수치 중심(§2)이며, 목표에서 제시한 기준과 1:1로 대응해야 한다.
- 쓰면 안 되는 것: 목표에 없던 새 기준으로 성과를 사후 정당화. 근거 수치 없는 정성적 표현("좋은 반응을 얻었다")만 단독으로 사용.
- 채용담당자: 빠른 스크리닝의 핵심 구간(`docs/INFORMATION_ARCHITECTURE.md` §2.4) — 성과를 낸 프로젝트인지 즉시 판단.
- 시니어 기획자: 목표-결과의 정합성과 수치의 신뢰성(과장 여부).

#### 9. 회고 (`retrospective`)

- 써야 하는 것: 결과 이후 스스로 발견한 한계·배운 점과 다음에 어떻게 적용할지. 아쉬운 점을 포함하는 것을 권장한다.
- 쓰면 안 되는 것: 문제 정의/접근 과정(4, 5번)의 요약 재서술. 회고를 성과 자랑으로 대체. 근거 없는 자기비하나 감정적 표현(§6).
- 채용담당자: (2차 대상) 성숙도·자기 인식 신호로만 참고.
- 시니어 기획자: 실패를 인정하고 구조적 개선안을 도출하는 능력 — 주니어와 시니어를 가르는 핵심 신호.

### 3.3 데이터 작성 템플릿

`data/projects.template.json`은 `docs/DATA_MODEL.md` §5와 100% 동일한 필드를 갖춘 빈 템플릿이다. 값은 전부 `""`/`[]`(불리언은 `false`)이며, 실제 콘텐츠를 추가할 때 이 템플릿을 복사해 `data/projects.json` 배열에 항목으로 붙여넣는다. 필드를 추가하거나 삭제하지 않는다 — 새 필드가 필요하면 먼저 `docs/DATA_MODEL.md`를 갱신하는 Architecture Decision을 거친다.

배열 필드 안에 들어가는 개별 항목의 모양은 다음과 같다(`docs/DATA_MODEL.md`의 해당 절 참고):

**`systems`의 항목 하나 (`ProjectSystem`, §5.3 · 작성 원칙은 위 3.2의 "6. 시스템 설계", §4 참고)**

```json
{
  "name": "",
  "purpose": "",
  "playerExperience": "",
  "structure": "",
  "flow": "",
  "data": "",
  "exceptionHandling": "",
  "expectedEffect": ""
}
```

**`features`의 항목 하나 (`ProjectFeature`, §5.4 · 작성 원칙은 위 3.2의 "7. 핵심 기능")**

```json
{ "name": "", "description": "" }
```

**`documents`의 항목 하나 (`ProjectDocument`, §5.6 · `type`은 `"pdf" | "ppt" | "docx" | "markdown" | "notion" | "other"`)**

```json
{ "type": "", "title": "", "url": "" }
```

**`gallery`의 항목 하나 (`ProjectGalleryImage`, §5.7 · `type`은 `"screenshot" | "wireframe" | "uml" | "erd" | "concept" | "other"` · 설명·캡션·목적은 §7 필수)**

```json
{ "type": "", "src": "", "description": "", "caption": "", "purpose": "" }
```

**`links`의 항목 하나 (`ProjectLink`, §5.8 · `type`은 `"github" | "figma" | "notion" | "youtube" | "deployment" | "other"`)**

```json
{ "type": "", "label": "", "url": "" }
```

`type` 필드들은 전부 닫힌 집합(union)이라 위 목록 중 하나의 문자열 값으로 채운다 — 빈 문자열로 남겨두지 않는다(다른 문자열 필드와 달리 `type`은 렌더링 분기 기준이라 항상 유효한 값이 있어야 한다).

## 4. 시스템 기획 작성 규칙

시스템 기획 문서는 항상 다음을 포함한다.

- 목적
- 플레이어 경험
- 시스템 구조
- 플로우
- 데이터
- 예외 처리
- 기대 효과

---

## 5. 게임 분석 작성 규칙

게임 분석 문서는 항상 다음을 포함한다.

**분석 대상과 목적** (분석 전체를 소개하는 도입 정보)
- 분석 대상 — 어떤 게임을 분석하는지
- 분석 목적 — 이 분석으로 무엇을 보여주려는지

**분석 관점 (시스템 / 콘텐츠 / UX)** — 세 관점 각각에 아래 4가지를 동일하게 적용한다 (`docs/DATA_MODEL.md` §6.2의 systemAnalysis/contentAnalysis/uxAnalysis에 대응).
- 핵심 요소 — 이 관점에서 가장 중요하게 다루는 대상 (예: 시스템 관점 → 핵심 시스템, 콘텐츠 관점 → 핵심 콘텐츠, UX 관점 → 핵심 경험)
- 장점
- 문제점
- 개선안

**결론** — 세 관점을 종합한 결론. 배운 점을 포함한다.

순서를 임의로 바꾸지 않는다.

> **변경 이력**: 이전에는 "분석 대상/분석 목적/핵심 시스템/장점/문제점/개선안/배운 점"을 하나의 평평한 7개 목록으로 나열했다. 이는 서로 다른 두 추상화 수준 — 분석 전체의 도입 정보(대상/목적)와, 시스템 관점에만 한정된 것처럼 보이지만 실제로는 세 분석 관점 모두에 반복 적용되어야 하는 4항목 템플릿(핵심 요소/장점/문제점/개선안) — 을 구분 없이 섞고 있었다. "핵심 시스템"이라는 표현도 콘텐츠·UX 관점에는 그대로 쓸 수 없어 "핵심 요소"로 일반화했다. 개념(7개)은 그대로 유지하고 계층만 명확히 했다 — `docs/DATA_MODEL.md` §6, `types/analysis.ts`와 함께 동기화되었다.

---

## 6. 문체

채용 담당자를 대상으로 한다.

- 객관적으로 작성한다.
- 전문적으로 작성한다.
- 읽기 쉽게 작성한다.
- 불필요한 감정 표현을 금지한다.

---

## 7. 이미지 사용 규칙

이미지는 반드시 다음을 가진다.

- 설명 (이미지가 무엇을 보여주는지)
- 캡션 (짧은 요약 문구)
- 목적 (이 이미지를 넣은 이유)

설명·캡션·목적이 없는 이미지는 사용하지 않는다.

---

## 8. PDF 작성 규칙

PDF는 웹과 동일한 구조를 유지한다.

- 섹션 순서는 웹 페이지 구조를 따른다.
- 웹에 없는 내용을 PDF에만 추가하지 않는다.
- 웹과 PDF의 정보가 서로 다르지 않도록 유지한다.

---

## 9. 체크리스트

문서를 작성하기 전에 다음을 확인한다.

- [ ] 콘텐츠 유형(프로젝트/시스템 기획/게임 분석)에 맞는 구성 순서를 따랐는가
- [ ] 각 항목에 근거(수치, 데이터, 사례)가 포함되어 있는가
- [ ] 결과뿐 아니라 과정(문제 정의 → 접근 → 설계)이 드러나는가
- [ ] 불필요한 미사여구나 감정 표현이 없는가
- [ ] 문체가 객관적이고 전문적인가
- [ ] 모든 이미지에 설명·캡션·목적이 포함되어 있는가
- [ ] PDF 버전이 웹 구조와 동일한가
- [ ] 문서 내 수치와 사실이 정확한가
